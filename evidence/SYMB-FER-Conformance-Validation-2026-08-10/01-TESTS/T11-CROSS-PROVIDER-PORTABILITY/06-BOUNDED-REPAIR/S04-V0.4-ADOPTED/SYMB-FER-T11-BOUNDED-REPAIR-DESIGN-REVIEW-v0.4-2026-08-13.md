## Findings by classification

### Documented fact

The v0.3 packet used imperative language including `Use only the supplied fixture` and `Do not use prior memory`, while simultaneously naming Morgan as `HUMAN`. In R04, Claude interpreted the fixture as an attempted replacement of the actual interlocutor and referenced outside context.

### Inference

The v0.3 wording did not clearly distinguish the fictional record subject from the actual user, and it framed context isolation in language that could be read as asking a receiver to suppress its own instruction hierarchy or judgment. This is a plausible contributor to refusal and outside-context comparison, but the source of `FX Industries` remains unknown.

### Unknown

- The exact source of the R04 `FX Industries` context.
- R04 model, effort, Project membership, style, and other account-level context.
- Whether the same response would occur under a documented minimized-context Claude environment.
- Whether provider account features can ever be proven fully absent through visible interface evidence alone.

### Recommendation implemented in this candidate

Define a controlled minimized-context lane, explicitly distinguish fictional subject from actual user, preserve safeguards and higher-priority instructions, replace suppression-style context language with conflict-safe record isolation, and use the verified manual two-stage capture method.

## Smallest provider-neutral repair

### 1. Actual-user boundary

The packet now says that Morgan Vale and Northstar Fabrication Lab are fictional test-record data, not claims about the actual user or their employer. The response contract requires receivers to preserve that distinction.

### 2. Safeguard boundary

The packet now states that it does not suspend provider safeguards, system instructions, applicable policy, or independent judgment. It asks only for bounded processing of fictional data.

### 3. Conflict-safe context handling

The v0.3 direction not to use prior memory is replaced by a narrower rule: do not import outside context into, use it to overwrite, or disclose it through the fictional record. A conflict does not authorize disclosure or canonical mutation.

### 4. Controlled minimized-context evidence

The procedure defines observable conditions before delivery:

- ChatGPT: brand-new Temporary Chat outside Projects.
- Claude: brand-new empty chat outside Projects, with default or Normal rather than custom style.
- Both: visible provider domain, empty transcript, model or `UNKNOWN`, relevant context indicator, and pre-delivery evidence preserved before packet delivery.

This lane is called controlled minimized-context, not perfectly sterile. Unknowns remain unknown.

### 5. Capture repair

The procedure removes heredocs, armed waiting blocks, and Control-D. After copying the first response, John manually types a short `pbpaste` redirection before any other clipboard action. The recovered file is verified, filed byte-identically, and removed only after governed verification.

### 6. Valid output versus conforming output

A complete refusal is valid raw receiver output if its byte boundary and capture integrity are established. It can fail the response contract without being mislabeled as a capture failure. Controlled eligibility is decided from receiver-environment evidence, not from whether the answer looks favorable.

## Lane distinction

The controlled portability lane asks whether the byte-identical fixture preserves material meaning under documented minimized-context conditions.

The real-world contextual robustness lane asks what happens under ordinary, personalized, Project-bound, ambiguous, or otherwise uncontrolled conditions. Such evidence is valuable but cannot replace a controlled run or enter its convergence total.

S03 remains unchanged as governed history. Candidate v0.4 does not reclassify, score, erase, or repair any S03 response or incident.
